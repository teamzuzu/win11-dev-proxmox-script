# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this repo is

A small collection of files that automate building a Windows 11 development VM on Proxmox VE from the host shell:

- **`win11.sh`** — the main script. Creates the VM (`qm create`/`qm set`), sources `download-isos.sh` to locate/download the Windows 11 and VirtIO ISOs, builds an unattended-answer-file ISO from `autounattend.xml` (via `genisoimage`), attaches everything to the new VM, then **starts the VM itself** and sends Enter via `qm sendkey` for ~15s to clear Windows Setup's boot prompt (see dedicated section below) — this is genuinely hands-off end to end, not just up to VM creation.
- **`download-isos.sh`** (added 2026-09-13) — `validate_iso_filename()`, `download_windows_iso()`, `download_virtio_iso()`, and `VIRTIO_STABLE_URL`, extracted out of `win11.sh` at the user's request. `win11.sh` sources it (`source "$SCRIPT_DIR/download-isos.sh"`); it can also be run directly (`./download-isos.sh`) to pre-fetch both ISOs without creating a VM — see the dedicated section below for how the dual-mode (sourced vs standalone) design works.
- **`autounattend.xml`** — Windows unattended-setup answer file. Creates a local `Admin` user, disables telemetry/consumer features/search suggestions, forces the network to Private and disables the firewall entirely, enables RDP and OpenSSH, and uses `FirstLogonCommands` to install Chocolatey, then Git and Visual Studio 2022 Professional.
- **`README.md`** — user-facing usage docs.

There used to be a separate `install.sh` wrapper and a file named `Proxmox script.sh`; both were removed/renamed to `win11.sh` in history. Don't reintroduce references to either filename.

These scripts are meant to run **on the Proxmox host** (needs `qm`, `pvesm`, `genisoimage` on PATH) with `autounattend.xml` and `download-isos.sh` present in the same working directory as `win11.sh`. There is no test suite — it can't be meaningfully unit tested outside a real Proxmox host, so treat any change as needing careful manual/read-through review rather than `npm test`-style verification. `autounattend.xml` itself CAN be checked for well-formedness without a Proxmox host: `python3 -c "import xml.dom.minidom as m; m.parse('autounattend.xml')"` - always run this after editing it. `win11.sh`/`download-isos.sh` CAN be smoke-tested without a real Proxmox host by putting fake `sudo`/`qm`/`pvesm`/`genisoimage`/`curl`/`wget` shims earlier on `$PATH` that just echo their arguments and touch/write fake output files — this is how the extraction below was verified end-to-end (found-locally path, download path, and standalone mode) before committing.

## Auto-start + clear the "Press any key" boot prompt (2026-09-13)

The Windows install media's UEFI bootloader shows "Press any key to boot from CD or DVD..." and waits only a few seconds before falling through to the next boot device (`ide3`/`sata0`/`scsi0` in our boot order, none of which are bootable OS images at that point) - without a keypress this silently defeats full automation, since nobody's watching the console at exactly the right moment on a scripted deploy. The user asked directly whether this could be worked around.

Two known approaches, and why the first was chosen:
1. **`qm sendkey` (implemented)** - inject a virtual keypress into the VM's console via Proxmox's QMP-backed `qm sendkey <vmid> <key>`. No ISO modification, no risk of producing a subtly non-bootable image, works immediately from very early boot.
2. **Patch the ISO** (not implemented) - replace `efi/boot/bootx64.efi` with `efi/boot/cdboot.efi` inside the Windows ISO (functionally identical except it skips the prompt) - a well-documented community technique, but requires re-mastering a hybrid El Torito/UEFI ISO correctly (`oscdimg`/`xorriso` with matching boot-catalog parameters), which is easy to get subtly wrong from a Linux host and would need re-doing whenever the Windows ISO changes. Not worth the added risk when option 1 is simpler and safer.

Implementation: `win11.sh` now calls `sudo qm start "$VMID"` itself right after the boot-order/agent/tablet `qm set` calls (previously this was left as a manual "Next Steps" instruction - it no longer is), then loops `sudo qm sendkey "$VMID" ret` every 1 second for 15 iterations (~15s total). Sending Enter after Setup has already moved past that screen is harmless - unattended Setup has no focused text/button control that would react to a stray keypress in a way that changes behavior. Verified end-to-end with the fake-binary-shim harness (see below); the mocked `qm sendkey`/`qm start` calls confirmed the loop count, ordering, and that `set -e` doesn't trip on it (`|| true` guards each iteration).

**Updated 2026-09-13, shortened from 90s to 15s**: originally set to 45 iterations/2s (~90s) to comfortably cover OVMF POST + ISO boot time variance across different host hardware, but the user found on live hardware that the boot prompt clears well within 15s and the extra ~75s was just dead time waiting on the script. If this turns out to be too short on slower/different host hardware (keypresses stop before the prompt actually appears), lengthen it again rather than assuming 15s is universally enough.

If this loop ever needs lengthening/shortening, it's the `for _ in $(seq 1 15); do ... sleep 1; done` line right after `qm start` - keep the sleep interval and iteration count as one clearly-named pair, don't split the total duration across multiple magic numbers.

## Quieted noisy tool stdout (2026-09-13, revised twice same day: stderr, then the actual call site)

`qm set --scsi0`/`--efidisk0`/`--tpmstate0` and `genisoimage` all print a lot of chatter that isn't useful to a user (LVM `lvcreate`/`lvchange` messages, `swtpm_setup` TPM-manufacturing output, OVMF varstore-copy `INFO:` lines, ISO9660 build stats), replaced with a short `success "..."` line after each so the user still gets positive confirmation the step actually completed, rather than either raw tool spam or silence.

**Originally this only redirected stdout to `/dev/null`, on the assumption that Proxmox/Perl tooling sends real errors to stderr and stdout was just chatter.** First revision (still wrong) assumed `swtpm_setup`'s noise came from the `--tpmstate0` `qm set` call and just widened that redirect to stderr too. Live-testing (2026-09-13) showed the noise is still there, and actually happens **after `qm start`, not at any `qm set` call** - `--tpmstate0 ...,size=0` only registers a placeholder; Proxmox defers actually provisioning/manufacturing the TPM state (running `swtpm_setup`) to first VM start, since that's the point it's first needed. So the real fix was quieting `sudo qm start "$VMID"` itself, not the `qm set` calls. `genisoimage`'s build stats are conventionally stderr too (mkisofs/genisoimage lineage) and *are* produced at the `genisoimage` call site, so that one redirect was correctly targeted from the start.

Fixed properly with a `run_quiet()` helper (defined next to the `info`/`success`/... color helpers) that captures **both** stdout and stderr via `output=$("$@" 2>&1)`, stays silent when the command exits 0, and on nonzero exit echoes the full captured output to stderr before `return`ing the real exit code - so `set -e`/`trap cleanup ERR` still fire exactly as before, and no diagnostic detail is lost on an actual failure (the thing the original stdout-only redirect was trying to protect, now achieved without depending on which stream a given tool happens to use, or which call site actually produces it). `--scsi0`, `--efidisk0`, `--tpmstate0`, `genisoimage`, and now `qm start` all go through `run_quiet` instead of a bare `> /dev/null`.

**If more post-start noise ever surfaces** (e.g. from the `qm sendkey` loop, unlikely since it discards stdout already via `2>/dev/null || true`), the same pattern applies - don't assume a tool's chatter appears at the call site that superficially seems responsible (TPM state is configured by `--tpmstate0` but actually manufactured by `qm start`); check where it's actually printed before wrapping the "obvious" line.

If you add a new noisy privileged command, wrap it the same way (`run_quiet sudo <cmd> ...`) rather than reaching for `> /dev/null` again - don't assume a tool's chatter is on stdout without checking, `run_quiet` sidesteps that question entirely.

Verified with a standalone harness (`test_run_quiet.sh`, not committed) exercising `run_quiet` directly: a command printing to both stdout and stderr then exiting 0 produced no output at all, and the same command exiting nonzero dumped both streams' content and propagated the real exit code. Previously verified with the fake-binary-shim harness that the four calls' original stdout redirection suppressed `NOISY:` stdout lines end-to-end; that harness would need mocked shims that write to stderr to re-verify the stderr-capturing fix the same way.

## download-isos.sh extraction (2026-09-13)

At the user's request, `validate_iso_filename()`, `download_windows_iso()`, `download_virtio_iso()`, and `VIRTIO_STABLE_URL` were moved out of `win11.sh` into a new `download-isos.sh`. Design:

- **`win11.sh` sources it**, via `SCRIPT_DIR=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd); source "$SCRIPT_DIR/download-isos.sh"` - resolved relative to the script's own location, not the caller's `$PWD`, so it works regardless of what directory `win11.sh` is invoked from. Sourcing (not exec'ing as a subprocess) was chosen deliberately: the download functions set `WIN_ISO`/`VIRTIO_ISO` as side effects that `win11.sh` reads afterward, and a subprocess model would need a stdout-only return-value protocol (fragile alongside the progress/log output these functions already print) instead of just sharing shell state directly.
- **`download-isos.sh` still works standalone** (`./download-isos.sh`, to pre-fetch both ISOs without creating a VM) via the classic `if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then ... fi` guard - that block only runs when the file is executed directly, not sourced, and does its own `$ISO_PATH_ROOT` resolution (only if not already set by a sourcing parent) plus the same search-then-download flow `win11.sh`'s Checks section normally drives.
- **Colors** (`info`/`success`/`warn`/`error`/`banner`): rather than duplicating win11.sh's ANSI color logic, `download-isos.sh` defines plain (uncolored) fallbacks guarded by `declare -F name > /dev/null || name() { ... }` - when sourced from win11.sh (which defines these first), the guards see the functions already exist and skip redefining, so output stays colored; when run standalone, the plain fallbacks kick in. Don't add win11.sh's ANSI color codes into download-isos.sh directly - that would duplicate the `[ -t 1 ]` terminal-detection logic in two places that could drift apart.
- **sudo preflight** and **`ISO_STORAGE_ID` default** are duplicated (not guarded) in `download-isos.sh`, since both are cheap/idempotent regardless of whether win11.sh already did them (`sudo -v` just refreshes the timestamp; `ISO_STORAGE_ID="${ISO_STORAGE_ID:-local}"` preserves whatever win11.sh already set).
- **What did NOT move**: colors, the sudo preflight block, `ISO_PATH_ROOT` resolution (`get_iso_path`/`DUMMY_PATH`), and the cleanup trap all stayed in `win11.sh`, because they're used well beyond just ISO downloading (the cleanup trap tears down the whole VM; `ISO_PATH_ROOT` is also used by the answer-file ISO generation and the "search for existing ISO" logic). Only the download-specific functions and the one constant they use moved.
- **Verified with fake `sudo`/`qm`/`pvesm`/`genisoimage`/`curl`/`wget` shims on `$PATH`** (see the note above) end-to-end in three configurations: both ISOs found locally, VirtIO ISO missing and downloaded (confirming `VIRTIO_ISO` set inside the sourced function correctly propagates back to `win11.sh`'s `qm set --ide3` line), and `download-isos.sh` run standalone. All three completed successfully before this was committed.

## QEMU Guest Agent installed inside the guest (2026-09-13)

`win11.sh` already passed `--agent enabled=1,fstrim_cloned_disks=1` to `qm set`, but that only tells **Proxmox** it should expect a guest agent to talk to on the QMP side - it does nothing to actually install the agent software inside Windows. Without the in-guest `qemu-ga` service running, Proxmox's guest-agent-dependent features (IP address reporting in the UI, `qm guest exec`, graceful ACPI shutdown via the agent instead of a raw power-off signal, `fstrim_cloned_disks` itself) silently don't work, even though the VM config looks like it has agent support enabled.

Added `Order 8` to `autounattend.xml`'s `FirstLogonCommands` (right after the debloat block, before the network/firewall changes; everything from the old `Order 8` onward was renumbered +1, now running through `23`): a PowerShell one-liner that enumerates CD-ROM drives via `Get-WmiObject Win32_CDROMDrive`, looks for `guest-agent\qemu-ga-x64.msi` on each, and runs `msiexec /i ... /quiet /norestart` on the first match.

**Why search drive letters instead of hardcoding one**, same reasoning as the WinPE `DriverPaths` fix above (see "Boot loop investigation"): the VirtIO ISO is attached at `ide3`, but with the Windows ISO + VirtIO ISO + OEMDRV all attached, Windows doesn't guarantee it lands on any particular drive letter by the time `FirstLogonCommands` runs. Enumerating `Win32_CDROMDrive` and testing each one for the actual file is the same fix applied one layer up (full-OS PowerShell instead of WinPE `DriverPaths` XML), and doesn't need the `autounattend.xml` `DriverPaths` widen-the-range workaround since PowerShell can just ask Windows directly which drives are optical instead of guessing letters.

`Start-Process -ArgumentList @(...)` (an array) was used rather than a single quoted argument string, specifically to avoid a second layer of quote-escaping inside the already-quoted `-Command "..."` value inside the XML `<CommandLine>` element - each array element becomes its own argument with no extra escaping needed. If you add more `msiexec`/external-process calls to `FirstLogonCommands`, prefer the array form for the same reason.

**Pitfall hit while writing this**: an XML comment placed right before this block originally read `--agent enabled=1...` as prose - XML comments cannot contain a literal `--` *anywhere* inside them (not just at the very start/end), so this broke `python3 -c "import xml.dom.minidom as m; m.parse(...)"` with `not well-formed (invalid token)`. Reworded to "Proxmox's `qm agent` option" instead. If you're writing a comment near here (or anywhere else in this file) that references a CLI double-dash flag like `--agent`/`--tpmstate0`/etc., don't put it inside an XML comment verbatim - rephrase around it or the well-formedness check will fail in a way that's easy to misdiagnose as something else.

Verified: `python3 -c "import xml.dom.minidom as m; m.parse('autounattend.xml')"` passes, the full `<Order>` sequence is contiguous 1-23 with no gaps/dupes, and the PowerShell logic (enumerate → find → build `msiexec` args) was dry-run tested against a fake CD-ROM/MSI path with `pwsh` and mocked `Get-WmiObject`/`Start-Process` functions, confirming it builds the correct `msiexec.exe /i <path> /quiet /norestart` invocation when the file is found and does nothing when it isn't.

## WSL + latest Ubuntu (2026-09-13, removed 2026-09-14)

**Removed at explicit user request on 2026-09-14**, along with VS Code (see the pgr2-recomp section above for the `visualstudio2022-workload-nativedesktop`/Chocolatey-package list that entry `18` "Install Git" now sits next to - VS Code was the entry right after it) - both `SynchronousCommand` entries are gone from `autounattend.xml`'s `FirstLogonCommands` and everything below renumbered to close the gaps. Kept this section as history/context rather than deleting it outright, since the reasoning below (why it can't be fully unattended, the nested-virtualization requirement) is exactly the kind of thing worth having on record if WSL is ever added back. If re-adding, re-read this whole section first rather than re-deriving it - the constraints haven't changed.

Originally added as `Order 24` (the last entry at the time) to `autounattend.xml`'s `FirstLogonCommands`: `wsl --install -d Ubuntu`. This is Microsoft's own documented one-command installer - it enables the required Windows optional features (WSL, Virtual Machine Platform), downloads the WSL2 kernel update, and downloads/stages the Ubuntu distro package, all without needing the Microsoft Store to be signed into an account (works fine from the local-only `Admin` account this script creates).

**"Latest Ubuntu"**: used plain `-d Ubuntu` (no version suffix) rather than pinning e.g. `Ubuntu-24.04`, since the unqualified `Ubuntu` distro name always resolves to whatever Canonical currently publishes as their default/latest release - pinning a version here would just mean this file goes stale every time Ubuntu ships a new LTS, the same "don't hardcode something that'll drift" reasoning as `VIRTIO_STABLE_URL`'s redirect-based approach.

**This cannot be made fully hands-off, unlike the rest of this script** - two hard blockers, neither fixable from `autounattend.xml`:
1. Enabling WSL/Virtual Machine Platform is a boot-config-level change (like enabling Hyper-V) that only takes effect after a restart. `FirstLogonCommands` run once, synchronously, in one logon session with no defined mechanism to resume the remaining queued commands after a mid-batch reboot - so this step deliberately does NOT try to force a restart itself (`wsl --install` doesn't restart automatically unless told to), to avoid cutting off whatever might run after it in the same batch.
2. Ubuntu's first launch (which happens automatically after the next restart, via a scheduled task Windows sets up) prompts interactively for a new UNIX username/password with no unattended/answer-file equivalent in a stock Ubuntu WSL image. This is a genuine interactive step - there's no supported way around it without building a custom preseeded WSL image, which is well outside this script's scope.

So the actual end-to-end experience is: `win11.sh` runs → WSL installs itself in the background during first logon → user restarts the VM once → user opens "Ubuntu" from the Start menu once and completes the one-time username/password prompt. Documented in README (Features list, Unattended Installation section, a new Troubleshooting entry) rather than silently leaving the user to discover this only on the CLAUDE.md side.

**Nested virtualization requirement**: WSL2 (the default WSL version on Windows 11) runs Linux inside a lightweight Hyper-V-based VM, so - since this whole Windows install is itself already a VM under Proxmox/KVM - the *Proxmox host's* CPU virtualization extensions need to be exposed one level deeper via KVM's nested-virtualization module option (`nested=1` for `kvm_intel`/`kvm_amd`). `win11.sh` already sets `--cpu host` on `qm create`, which passes VMX/SVM flags through correctly *as long as* the host has nested virtualization turned on - this is a host-level `modprobe` setting outside this script's control (documented as a Proxmox-host prerequisite in README, not something `win11.sh` can enable itself, since it requires host root and potentially a host reboot/module reload done in advance of VM creation, not during it). Without it, the `wsl --install` FirstLogonCommand step still succeeds (it's just downloading/staging packages), but the *actual* Ubuntu launch after restart will fail with a virtualization/Hyper-V error - this failure mode and how to confirm/diagnose it is in the README's new Troubleshooting entry.

Didn't add `--web-download` (an alternative `wsl --install` flag that fetches the distro via a direct web download instead of through the Microsoft Store infrastructure) since plain Store-based install is Microsoft's default documented path and is expected to work fine for a local-only account - if a future run hits a Store-access failure specifically (as opposed to the nested-virtualization failure mode above), that flag is the next thing to try.

Verified only via `python3 -c "import xml.dom.minidom as m; m.parse('autounattend.xml')"` (passes) and confirming the `<Order>` sequence is contiguous 1-24 with no gaps - the actual WSL/Ubuntu install behavior itself is untestable outside a real Windows 11 guest with nested virtualization actually working, same caveat as everything else in this file that depends on real Windows Setup/OOBE behavior.

## Deprovisioned "new Outlook for Windows" - fixes an unexpected region prompt during install (2026-09-13)

Live-testing turned up an unexpected region/country prompt appearing partway through an otherwise-unattended install, which the user suspected was Outlook-related. Researched rather than guessed (`WebSearch`/`WebFetch` against Microsoft's own ["Control Installing and Using New Outlook"](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/get-started/control-install) doc): Windows 11 builds later than 23H2 ship "new Outlook for Windows" (`Microsoft.OutlookForWindows`) preinstalled, and - the key detail - it's fetched via a **dedicated OOBE-time Windows Update Orchestrator scheduled task**, registered at `HKLM\SOFTWARE\Microsoft\WindowsUpdate\Orchestrator\UScheduler_Oobe\OutlookUpdate`. That task pulls the app from the Microsoft Store *during OOBE itself*, before any `FirstLogonCommands` run - a Store-driven install/first-run flow triggering a region/market prompt mid-setup lines up exactly with what was observed, and with the user's own suspicion that it was Outlook-related.

Originally fixed by adding `Order 2` to the **`specialize`-pass** `Microsoft-Windows-Deployment` `RunSynchronous` block (right after the existing `BypassNRO` registry command) - deliberately in `specialize`, not `FirstLogonCommands`, because `specialize` runs before OOBE even starts, and putting the fix in `FirstLogonCommands` instead (which only runs once the first user's first logon completes, i.e. after OOBE has already run) seemed like it would be too late to beat the OOBE-time task. **This placement was wrong and broke the installer - see the regression note immediately below before touching this again.**

The command (content unchanged by the regression fix, only its location moved):
```
Get-AppxProvisionedPackage -Online | Where-Object { $_.PackageName -like 'Microsoft.OutlookForWindows*' } | Remove-AppxProvisionedPackage -Online; Remove-Item -Path 'HKLM:\SOFTWARE\Microsoft\WindowsUpdate\Orchestrator\UScheduler_Oobe\OutlookUpdate' -Force -ErrorAction SilentlyContinue
```
- Uses `Get-AppxProvisionedPackage -Online | Where-Object {...} | Remove-AppxProvisionedPackage` (matching the pattern Microsoft's own doc uses for removing Mail/Calendar) rather than the doc's alternate one-liner `Remove-AppxProvisionedPackage ... -PackageName (Get-AppxPackage Microsoft.OutlookForWindows).PackageFullName` - `Get-AppxPackage` queries per-user AppX registration for the *current* user context, which doesn't reliably exist yet during `specialize` (no user profile has been created at that point); `Get-AppxProvisionedPackage -Online` queries the DISM image-provisioning store directly, which doesn't depend on any user context being live.
- The registry key removal is kept as a defensive extra even though Microsoft's doc says it's unnecessary "for any device that installed the March 2024 Non-Security Preview release (or later cumulative update) for Windows 11, version 23H2" - since this script can't know how recently-patched whatever Windows 11 ISO a user supplies is, removing a key that may already be gone is harmless (`-ErrorAction SilentlyContinue` swallows the not-found case cleanly).

**Scope deliberately kept to just Outlook**, per the explicit ask ("I don't want Outlook installed") - the same Microsoft doc also covers removing the legacy Mail/Calendar apps (`microsoft.windowscommunicationsapps`, since new Outlook is meant to replace them) and blocking Store access entirely; neither was done here, consistent with this file's standing rule of not expanding scope beyond what's asked (see the AppX bloatware-removal note in the pgr2-recomp section above) - mention these as available follow-ups if the user wants them, don't add silently.

### Regression, fixed 2026-09-14: the `specialize`-pass placement crashed Windows Setup ("the computer restarted unexpectedly")

Live-testing the `d8b6e41` commit (this Outlook fix + the pagefile change below) broke the installer outright - Setup got partway through and hit "the computer restarted unexpectedly", the classic signature of a `RunSynchronousCommand` returning a nonzero exit code in the `windowsPE`/`specialize` passes, which Windows Setup treats as fatal and responds to by aborting/rolling back rather than continuing.

Diagnosed by process of elimination first: the same commit also added a `FirstLogonCommands` entry (the pagefile change, below) - `FirstLogonCommands` failures are silent/non-fatal by design (see the Chocolatey-PATH-timing bug elsewhere in this file, which is a real example of a silent `FirstLogonCommands` failure that never crashed Setup), so that one was ruled out as the cause immediately, leaving the new `specialize`-pass command as the only plausible culprit.

**Most likely root cause** (unconfirmed without a live Setup debug log, but well enough understood to act on): `specialize` runs *during* Windows Setup's own servicing of the freshly-applied image. `Get-AppxProvisionedPackage`/`Remove-AppxProvisionedPackage` both go through the same DISM/CBS servicing stack Setup itself is actively using at that exact moment - invoking a second DISM-backed operation concurrently very plausibly collides with Setup's own servicing lock (a documented class of problem: DISM operations reporting "another servicing operation is in progress" when something else is mid-transaction), throws a terminating error inside the `-Command` script, and `powershell.exe` returns nonzero - fatal, per the above.

## Pagefile disabled at first logon (2026-09-13)

Added as the last entry (`Order` has shifted a few times since as other entries were added/removed - see the file itself for the current number) to `autounattend.xml`'s `FirstLogonCommands`, per explicit user request:
```
$cs = Get-CimInstance Win32_ComputerSystem; $cs.AutomaticManagedPagefile = $false; Set-CimInstance -InputObject $cs; Get-CimInstance Win32_PageFileSetting | Remove-CimInstance -ErrorAction SilentlyContinue
```
Turns off "automatically manage paging file size" and then deletes any existing pagefile setting, i.e. "No paging file" on every drive - the standard two-step needed since just clearing `Win32_PageFileSetting` while automatic management is still on lets Windows recreate one on next boot.

**Used the CIM cmdlets (`Get-CimInstance`/`Set-CimInstance`/`Remove-CimInstance`) rather than `wmic`** - `wmic` (the classic `wmic computersystem set AutomaticManagedPagefile=False` / `wmic pagefileset delete` one-liners you'll see in older guides) is deprecated and removed by default in newer Windows 11 builds, so a `FirstLogonCommands` step depending on it would silently no-op or fail depending on exactly which build the user's Windows 11 ISO is. CIM cmdlets are the current, non-deprecated equivalent and match the `powershell -Command "..."` pattern already used everywhere else in this file.

**Trade-off, not fixed further**: disabling the pagefile entirely means Windows can't write a memory dump on a crash (BSOD), which would otherwise be a first diagnostic step if something goes wrong. Reasonable for a disposable dev VM per the user's own request, but worth knowing if a future debugging session ever needs a crash dump and comes up empty - the pagefile being off here is why, not a missing/broken dump configuration.

Didn't touch `VM_MEMORY`/`DISK_SIZE` or Proxmox's own swap - this is Windows' in-guest virtual memory only, unrelated to whatever swap configuration exists on the Proxmox host itself (out of scope, host-level).

Verified: the PowerShell was dry-run tested with `pwsh` against mocked `Get-CimInstance`/`Set-CimInstance`/`Remove-CimInstance` cmdlets (using `[CmdletBinding()]` on the mocks so `-ErrorAction` binds as a common parameter the way it does on the real cmdlets) - confirmed it sets `AutomaticManagedPagefile = $false`, removes an existing pagefile setting object when one is returned, and doesn't error when the pipeline is empty. `python3 -c "import xml.dom.minidom as m; m.parse('autounattend.xml')"` passes, `<Order>` sequence is contiguous 1-25.

## Code comments vs. CLAUDE.md

This repo has a standing split between the two, and it applies to `win11.sh`, `autounattend.xml`, and any file added later:

**Goes in a code comment (short, factual, at the point of use):**
- What a non-obvious line does, in present tense, in one line. Two lines only if the thing genuinely needs a second clause (e.g. a regex's edge case).
- A pointer to more detail: `# ... (see CLAUDE.md)`.
- Never a paragraph. If you're about to write a second sentence justifying *why* something is the way it is, stop — that belongs below instead.

**Goes in CLAUDE.md (as much detail as the topic needs):**
- The *why*: root cause of a bug, the investigation that found it, what was tried and ruled out, what the fix actually changed and what it didn't.
- Anything that took more than a couple of minutes to figure out — if it was non-obvious to work out once, it'll be non-obvious to re-derive later.
- Decisions deliberately NOT made (e.g. "Windows 11 ISO auto-download was deliberately NOT added" below) and the reasoning, so they aren't re-attempted or re-litigated from scratch.
- Constraints on future edits to that area ("if you change X, Y must also change" / "don't do Z, it'll break because...").

**In practice:** when you fix something, write the one-line factual comment in the code, then add or extend a dated `##` section here with the full story. When you're about to touch code that has a `(see CLAUDE.md)` pointer, actually read the referenced section first rather than re-deriving the reasoning from the code alone - it may cover a constraint or a rejected alternative that isn't visible from the diff.

## Boot loop investigation (2026-09-13) — autounattend.xml missing xmlns:wcm, fragile driver-path assumption

Symptom: VM boots the Windows 11 ISO fine, reaches the initial Setup ("first blue screen"), then resets - before language selection - whenever the OEMDRV answer-file ISO (`sata0`) is attached. Removing `sata0` gets to the normal manual language-selection screen (expected - there's no unattend file to find/apply anymore, so it isn't really a fix, just confirms the crash happens *while trying to process the unattend file*).

Two real bugs found and fixed, in order of suspected impact:

1. **`autounattend.xml`'s root `<unattend>` element never declared `xmlns:wcm`.** Every `wcm:action`/`wcm:keyValue` attribute in the file (29 of them) referenced an undefined namespace prefix - `python3 -c "import xml.dom.minidom as m; m.parse(...)"` fails on this with `unbound prefix` even on the file as it existed before any of this session's edits, so this bug predates this repo's tracked history entirely. A real Windows System Image Manager-generated unattend.xml always declares `xmlns:wcm="http://schemas.microsoft.com/WMIConfig/2002/State"` alongside the default namespace. Whether Windows Setup's own unattend-processing engine is strict enough about this to be the actual crash cause is unconfirmed (untestable outside a real install), but it's a genuine, structurally-wrong file that's cheap and safe to fix regardless, so it was fixed immediately. If a boot loop recurs after this fix, this namespace bug is ruled out as the cause.
2. **`PnpCustomizationsWinPE`'s `DriverPaths` only checked `E:\` and `F:\`.** WinPE assigns CD-ROM drive letters based on how many optical devices are attached; with the Windows ISO + VirtIO ISO + OEMDRV all attached (3 optical devices), the VirtIO ISO isn't guaranteed to land on `E:` or `F:` - it could be `D:`, `G:`, or `H:`. If the viostor/NetKVM drivers aren't found, Windows Setup can't see the `scsi0` disk, and the automated `DiskConfiguration` step (`DiskID 0`, `WillWipeDisk`) has nothing to act on - a very plausible way to crash WinPE early. Widened the search to `D:` through `H:` for both driver dirs (10 `PathAndCredentials` entries total). Extra non-existent paths are silently skipped by Windows Setup, so this is purely additive/safe.

Both fixes above resolved the reset-before-language-selection loop. Setup then progressed further but reported no drives / no drivers found when the user pointed Setup's "Load Driver" at the VirtIO ISO manually - i.e. `viostor.inf` was on the disc but Windows didn't consider it a match.

3. **Wrong VirtIO driver family: `viostor` vs `vioscsi`.** `win11.sh` attaches the main disk via `--scsihw virtio-scsi-pci --scsi0 ...` - a VirtIO-**SCSI** controller. `viostor` is the driver for the older VirtIO-**BLOCK** device type, a different PCI hardware ID. Windows Setup's "Load Driver" dialog hides drivers that don't match hardware actually present by default, so `viostor.inf` being right there on the disc didn't help - it silently looked like "no driver found" because it's simply the wrong driver for this controller. Confirmed by downloading the actual stable-virtio ISO (`virtio-win-0.1.302.iso` as of this writing) in this sandbox and inspecting it with `isoinfo -R` - `/vioscsi/w11/amd64/vioscsi.inf` exists and is the correct match; `/viostor/w11/amd64/` also exists but is for a different bus type. Changed all the storage `DriverPaths` entries from `\viostor\w11\amd64` to `\vioscsi\w11\amd64`; `NetKVM` (network) was already correct and untouched. **If `win11.sh`'s disk is ever changed to attach via a virtio-blk device (e.g. `--virtio0`) instead of `--scsi0`/`virtio-scsi-pci`, switch these paths back to `viostor`** - the two must always match whatever bus type the script actually uses.

If a boot loop or missing-driver problem still recurs after all three fixes, the next diagnostic step (not yet tried) is pressing Shift+F10 at whatever screen it fails at to get a WinPE command prompt, and checking `wpeutil`/drive letters/`X:\Windows\Panther\setupact.log` directly.

**General lesson for this file:** don't trust unattend.xml driver/path assumptions from memory or convention - when in doubt, actually fetch and inspect the real ISO (`isoinfo -R -i <file> -l`) rather than guessing folder names or driver families, and cross-check the driver family against exactly which Proxmox bus/controller `win11.sh` attaches the disk with.

## Network/firewall/remote-access defaults (2026-09-13)

After the first successful end-to-end install, the user found SSH unreachable until manually switching the VM's network from Public to Private in Windows. Added to `FirstLogonCommands` (`autounattend.xml`), in this order, right after the debloat block and before Chocolatey:

## Bug found by live-testing: bare `choco` fails inside FirstLogonCommands (2026-09-13)

Symptom: Chocolatey itself installed fine, but none of `git`/`vscode`/`visualstudio2022professional` did - and there was no trace of them at all in `C:\ProgramData\chocolatey\logs\chocolatey.log`, while manually running the *exact same* `choco install git -y` command in a fresh session worked immediately.

Root cause: all `FirstLogonCommands` execute within one long-lived first-logon session. Chocolatey's installer (`Order 8`) appends `C:\ProgramData\chocolatey\bin` to the machine `PATH` via the registry, but that session's environment block was captured before the install ran, so every subsequent command in the same batch (`Order 12`-`14`, the `choco install ...` calls) resolves bare `choco` against a stale `PATH` and gets nothing - a silent `9009` ("command not found") with zero log trace, since `choco.exe` was never actually launched to log anything. Confirmed by the log being completely silent on `vscode` (not even a failed-attempt entry) combined with the manual command working fine in a new session.

Fixed by calling Chocolatey via its full path, `C:\ProgramData\chocolatey\bin\choco.exe`, instead of bare `choco`, in all three app-install commands (`Order 12`-`14`) - this sidesteps `PATH` resolution entirely regardless of session/environment timing. Don't use `%ChocolateyInstall%` as an alternative fix - that environment variable has the exact same staleness problem as `PATH` within the same session, so it wouldn't actually fix anything. If you add more `choco install` commands to `FirstLogonCommands` later, use the same full path, not bare `choco`.

**Same root cause resurfaces for the interactive user afterward (2026-09-13), one layer further out - user asked "do we need to configure the choco path as an ENV var?"**: no, nothing to configure. Git's own installer *does* correctly write itself to the system `PATH` (that part works fine, same as Chocolatey's own install). The trap is that this is still just a registry write - any session/shell that was already running before the write happened (including the very first interactive logon session, the one `FirstLogonCommands` itself runs inside) captured its environment earlier and won't see the update until it re-reads `PATH`, which only happens at a new logon. So a user testing `git` from a shell opened in that same first session can see "not recognized" even though the install genuinely succeeded and `PATH` is genuinely correct at the system level. Not fixable from `autounattend.xml` the way the choco.exe-calling-choco.exe case was (there's no "full path" equivalent for an interactive user just typing `git`) - the actual fix is logging off/on or rebooting once, which is what was told to the user rather than making a code change. If this comes up again, point here rather than assuming something's misconfigured - verify first whether `git.exe` actually exists on disk (`Get-Command git -ErrorAction SilentlyContinue` after a fresh logon, or check `C:\Program Files\Git\cmd` directly) before suspecting the install itself.

- Added `set -e` right after the shebang so a failed `qm create`/`qm set` actually stops the script instead of it reporting "VM created successfully!" over a half-configured VM. The restored `DUMMY_PATH=$(pvesm path ...) || true` line is deliberately guarded so a storage-resolution failure still prints the friendly error message instead of dying silently under `set -e`.
- Converted the file from CRLF to LF line endings — it had been CRLF since before the rename (the earlier "Fix line endings" commit only ever touched the old `install.sh`), which made `bash win11.sh` fail with a syntax error on the `case ... in` line. **If you see CRLF creep back in (e.g. someone edits/saves the file on Windows), reflow it (`sed -i 's/\r$//' win11.sh`) — the script does not run at all as CRLF.**

If you touch the ISO-handling or error-handling logic again, keep these in mind:
- Avoid combining `set -e` with `set -o pipefail` here without auditing every pipeline first — `download_windows_iso`'s `curl | grep | sed | tr` relies on `tr` (always exit 0) being last so a header-not-found `grep` miss doesn't kill the script; `pipefail` would break that.
- `pvesm path ...`/similar lookups that feed a "did this fail?" `if [ -z ... ]` check need `|| true` (or equivalent) so `set -e` doesn't short-circuit past the friendly error message.

## Bug found by live-testing: broken filename from Content-Disposition parsing (2026-09-13)

`download_windows_iso()`'s header-parsing regex (`sed -n 's/.*filename="\?\([^"]*\)"\?.*/\1/p'`) assumed the `filename=` value would either be quoted or be the last thing on the line. Microsoft's CDN sends an **unquoted** `filename=...` followed by a second `filename*=UTF-8''...` (RFC 5987) parameter on the same `Content-Disposition` line. With no quote to bound the unquoted capture, `[^"]*` swallowed the rest of the header line, saving the ISO on disk as literally `Win11_...iso; filename*=UTF-8''Win11_...iso` — which then broke `qm set --ide2` downstream with a confusing `400 Parameter verification failed` / "property is not defined in schema" error that gave no hint the actual problem was upstream in the filename. Fixed by also excluding `;` from the capture (`[^";]*`), verified against both quoted and unquoted real-world header shapes before committing. If a user already has a file with this corrupted name sitting in ISO storage from before the fix, it needs a manual `mv` to strip the header text back to a plain `....iso` name — the script can't detect/repair a file already on disk with this problem, only avoid causing it on future downloads.

Added a `validate_iso_filename()` guard (called after both `WIN_ISO` and `VIRTIO_ISO` are resolved, before anything is passed to `qm set`) that rejects any filename not ending in `.iso`, or containing `, ; = " '`, with a clear message pointing at the likely cause - so a similar problem (from any source, not just this one regex) fails fast with an actionable message instead of a cryptic Proxmox schema error several steps later. Keep this guard in place if you touch the ISO-resolution logic; it also validates any error-message escaping doesn't produce false positives on its own bracket-expression pattern - be careful with `\` inside a `[[ ]]` bracket expression when editing it, since backslash is *not* special there the way it is in other quoting contexts (a stray `\x`-style escape becomes a literal `x` in the character class, silently changing what it matches - test any edit to this pattern against both a clean filename and the broken one above before trusting it).

**Windows 11 ISO auto-download was deliberately NOT added.** It was investigated live on 2026-09-13: Microsoft's current download flow (`microsoft.com/software-download-connector/api/...`) sits behind a purpose-built, multi-step bot-detection handshake (`vlscppe.microsoft.com/tags` session whitelisting, then an `ov-df.microsoft.com` timing/fingerprint challenge requiring a `w`/`rticks` exchange, before the SKU/download-link calls will succeed) — this is confirmed by Fido (`pbatard/Fido`, the tool Rufus uses), whose own source comments call it Microsoft's "protection". The download page's markup also carries explicit anti-automation/anti-anonymization language with a threat of banning entities/locations that trigger it. Reproducing that handshake would mean baking a browser-spoofing bypass of a service's stated anti-bot control into this repo, on top of being fragile (breaks whenever Microsoft tweaks the handshake). Don't add this without the user explicitly re-confirming they want that trade-off; if asked again, point at this note rather than re-researching from scratch. The interactive "paste the direct link" flow in `download_windows_iso()` remains the supported path for the Windows ISO.

## Bugs found by live-testing on a real Proxmox host (2026-09-13)

Neither of these was catchable from this sandbox (no `qm`/`pvesm` available here) - both only surfaced once the user ran the script on their actual Proxmox host. If you change anything touching `pvesm`/`qm` argument syntax, get it tested on a real host before assuming it's correct, regardless of how it reads:

- **`pvesm path` probe filename needs a real extension.** The `ISO_PATH_ROOT` resolution used `iso/dummy` as a throwaway filename to resolve. Proxmox's volume-id parser for content type `iso` requires the name to end in `.iso` or `.img`; an extension-less name fails to parse *before* `pvesm` gets anywhere near building a path, regardless of whether the storage is actually fine. Fixed by probing `iso/dummy.iso` instead. If you add other `pvesm path`/volid-parsing calls, always use a syntactically valid volume name for the content type, even for throwaway/nonexistent lookups.
- **Disk allocation size must be a bare number, no unit suffix.** `DISK_SIZE="130G"` fed into `qm set --scsi0 $DISK_STORAGE:$DISK_SIZE,...` produced `unable to parse lvm volume name '130G'`. Proxmox's `storage:SIZE` allocation syntax expects `SIZE` to be a plain integer number of GiB - a suffix like `G` makes it try to parse `130G` as the name of an *existing* volume to attach rather than a size to allocate. Fixed by using `DISK_SIZE="130"` (later changed to `"128"` per user preference). `--efidisk0`/`--tpmstate0` use size `0` (Proxmox auto-sizes these), which is unaffected.
- **`qm set`'s `storage:...` argument needs quoting.** `qm set $VMID --ide2 $ISO_STORAGE_ID:iso/$WIN_ISO,media=cdrom` (and the equivalent `--ide3`/`--sata0`/`--scsi0`/`--efidisk0`/`--tpmstate0` lines) were unquoted, so a `WIN_ISO`/`VIRTIO_ISO` filename containing a space (very plausible for a Windows ISO downloaded via browser) gets word-split by bash into multiple `qm` arguments, failing with `400 too many arguments`. Fixed by quoting the whole `"$STORAGE:...` string as one argument on every `qm set`/`qm create`/`qm status` call that takes a variable. If you add a new `qm` invocation, quote it too - don't assume filenames/names are space-free.
- **Cleanup trap now also destroys a partially created VM.** Once `qm create` succeeds, `VM_CREATED=1` is set; `cleanup()` (the same `trap ... ERR` used for the OEM ISO) now also runs `qm destroy "$VMID" --purge 1` if `VM_CREATED=1`, so a later failure (e.g. the ISO-attach bug above) doesn't leave a half-built VM blocking retries with the same `-i` VMID. This only protects runs *after* this fix landed - a VM left over from an earlier failed run still needs a manual `qm destroy <vmid>`.

## Runs as a non-root user via sudo (added 2026-09-13)

Every external command that needs privilege - `qm`, `pvesm`, `genisoimage`, and any file operation that touches ISO storage (`wget`/`curl` downloads, `find`/`stat`/`basename`/`sort`/`tail`/`head` on `$ISO_PATH_ROOT`, `mktemp`/`cp`/`sed`/`rm` for the temp answer-file dir, `rm`/`qm destroy` in the cleanup trap) - is now prefixed with `sudo`, so the script can be run as a regular sudo-capable user instead of requiring `root`. A preflight block right after the color helpers checks `command -v sudo` and `sudo -v`, exiting with a clear message if either fails, rather than dying confusingly on the first privileged command.

**Deliberately NOT sudo'd, because it would break the script:**
- `command -v curl/wget/genisoimage/sudo` - `command` is a bash builtin, not a real binary; `sudo command -v x` fails with "command not found".
- Bash builtins/keywords: `read`, `echo`, `printf`, `[[ ]]`/`[ ]`, `local`, `return`, `exit`, `trap`, the `if`/`while`/`case` control structures themselves.
- This script's own functions (`info`/`success`/`warn`/`error`/`banner`/`validate_iso_filename`/`get_iso_path`/`download_windows_iso`/`download_virtio_iso`/`cleanup`) - sudo execs real binaries by name, it can't invoke a function defined in the calling shell.
- `[ ! -f "$ANSWER_FILE" ]` - checks a file in the user's own working directory (the cloned repo), not on ISO storage, so no privilege is needed.

If you add a new external command, sudo it if it touches `qm`/`pvesm`/ISO storage; if it's a plain read on something the invoking user already owns (like `$ANSWER_FILE`), don't. `[ -f ... ]`/`[ ! -f ... ]` checks on `$ISO_PATH_ROOT` paths were changed to `sudo test -f ...` (`test` is both a builtin and a real binary at `/usr/bin/test`, so this form works correctly under `sudo`) - do the same for any new existence checks on privileged paths.

## Other things to keep in mind when touching `win11.sh`

- The admin password is passed as a plaintext CLI arg (`-p`) and written in plaintext into the generated `autounattend.xml` (`PlainText>true`), so it lands in shell history, `ps` output, and on the ISO storage as an unencrypted file. Treat this as a dev/lab-only tool, not something to point at production credentials. Not fixed — flagged for awareness only.
- `autounattend.xml` sets `LogonCount>999` under `AutoLogon`, i.e. the VM auto-logs-in as `Admin` indefinitely across reboots. That's convenient for a throwaway dev VM but worth calling out if this is ever adapted for anything longer-lived.
- The firewall is fully disabled and RDP+SSH are both open (see "Network/firewall/remote-access defaults" above) - combined with the plaintext/default password, this is a materially more exposed VM than a stock Windows install. Fine for an isolated home-lab network by explicit user request; don't quietly make this "more secure by default" without being asked, but also don't let new features widen the exposure further without flagging it.

## Conventions

- Bash, `#!/bin/bash`, matches the existing style in `win11.sh` (plain functions, `getopts` for flags, human-readable `echo` progress banners).
- Colored output (added 2026-09-13): `info`/`success`/`warn`/`error`/`banner` helper functions near the top wrap `printf` with ANSI codes (cyan/green/yellow/red/bold-cyan respectively); `error` writes to stderr, the rest to stdout.
